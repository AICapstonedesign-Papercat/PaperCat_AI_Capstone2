🐱 PaperCat이 뭐 하는 서비스인지, 5줄로
  1. 뭘 만드나 — 영어 논문이 어려워서 못 읽는 비전공자를 위해, 논문을 큐레이션→쉬운 이야기로 변환→질문하면 답변→한줄요약 채점→도감에 모으는 웹 서비스. 캡디1(앱, 가짜데이터)을 캡디2에서 웹으로 옮기고 진짜 데이터·진짜 AI로 바꿉니다.
  2. 왜 ChatGPT랑 다른가 — 답변을 그 논문 안으로만 제한하고, 모든 문장에 "몇 번째 문단에서 나온 말인지" 링크를 달고, 근거 없으면 모른다고 솔직히 말합니다.
  3. 어떻게 안전장치를 두나 — AI가 거짓말(환각)할 수 있으니, 답변 형식 검사·출처 존재 검사·사람이 정답 매긴 기준과 비교하는 자동 채점을 겹겹이 둡니다.
  4. 얼마나 하나 — 20편을 한번에 하지 않고, 우선 논문 3편으로 전체 과정을 끝까지 돌려봅니다(P1). 채점 기준·평가 문항은 그동안 미리 준비(P2 병렬), 3편이 통과하면 숫자 기준으로 20편 확장(P3)→여유 되면 부가기능(P4) 순서로 갑니다.
  5. 지금 뭐가 안 정해졌나 — 백엔드 구조(후보 A vs B')는 김성민이 학기 시작 1주차에 정합니다. 프론트는 iPad 앱(bare React Native, Expo 제외)으로 확정 — 캡디1의 iOS 네이티브 앱 설계를 계승해 화면만 iPad로 확장합니다.

차별점 1

차별점 2

차별점 3

근거 없으면 명시적 거절

RAG를 쓴다고 모델의 배경지식·환각이 완전히 차단되는 건 아닙니다 — "차단"이 아니라 "원문 근거를 우선 사용하도록 설계하고, 근거 없는 답은 거절"이 정확한 표현입니다.
↓ 근거 연결과 그 검증은 서로 다른 문제입니다
① 자동 검증 (기계가 즉시 확인)
스키마 검증 근거 문단 ID 존재 검증
② 충실성 검증 (그 근거가 주장을 실제로 뒷받침하는가 — LLM 평가 + 사람 표본 검수)
골든셋 회귀 테스트 RAGAS 충실성 지표 침묵 실패 모니터링(주1회 수동 표본)
①은 "문단 ID가 존재하는가"를 기계가 즉시 확인합니다. ②는 "그 문단이 주장을 실제로 뒷받침하는가"를 LLM 평가 + 사람 표본 검수로 별도 확인합니다 — 인용 연결(①)과 충실성(②)을 같은 것으로 보여주지 않습니다.
주의: "이해도 향상"(입문 장벽 완화)은 사용성 테스트로 이번 범위에서 직접 측정합니다. 다만 도감·경험치·스트릭 같은 게이미피케이션이 지속 사용을 높이는지는 별개 메커니즘이며 이번 범위에서 증명하지 않음 — 둘을 섞지 않습니다.

(1) iPad 앱 전환

캡디1이 이미 iOS 사이즈 네이티브 앱(21화면·도감카드·배지·디자인시스템 12원칙)으로 설계돼 있었다. 캡디2는 이 설계를 실데이터·실 LLM으로 완성하며 iPad(최신 모델)를 메인 타겟으로 화면을 확장한다 — 배포 테스트용 포장이 아니라 실제 개발 대상. iPhone 전용 디자인은 iPad 완료 후 팀이 원할 때 별도 착수(학기 내 고정 일정 아님). "앱 형태"는 캡디1 계승(근거 있음), "iPad 화면 크기가 유저에게 최적"이라는 주장은 검증 전 가설(1차 AEIOU 데스크톱 관찰과 비교 검증 예정) — 둘을 섞지 않는다.

(2) 논문 실데이터 연동 · 원문 수집 파이프라인

처음부터 20편이 아니라 기준 논문 3편으로 수집→RAG→채점→도감 수직 슬라이스를 먼저 완성.

확장 게이트: 3편 전 과정 동작 + DB 사용량이 무료 티어 한도의 70% 미만일 때만 20편까지 확장. 70%는 팀 운영 기준(외부 한도 아님), 실측 오차 버퍼. 기준 DB가 Atlas M0(512MB)에서 Supabase 무료 티어로 바뀌었으므로 S1에서 실측 재확인 필요(§6).

사전 추정(역산): 임베딩 1536차원(≈6KB/벡터), 논문당 40~60문단 청킹 시 벡터+인덱스 오버헤드 포함 논문당 약 0.6~1MB. 3편 ≈2~3MB, 20편 확장해도 ≈12~20MB로 70% 임계(≈358MB) 대비 여유 큼 — 근사치이며 S1 실측으로 확정 필요.

지원 섹션은 Abstract·Introduction·Method 우선. 수식·표·그림 질의는 초기 버전 범위 밖.

실측으로 뒤집힌 항목 (v3.4) — 기존 규칙은 "CC BY 등 변형 허용 라이선스 논문만 적격"이었다. arXiv OAI-PMH로 대표 논문 18편의 라이선스를 실제 조회한 결과 CC BY는 LLaMA 1편뿐이었다. Attention·BERT·ResNet·ViT·CLIP·PPO·Stable Diffusion 등은 모두 arXiv nonexclusive-distrib (저자가 arXiv에만 배포권을 준 것, 2차 변형·재배포 권리 없음). Attention의 원 게재처인 NeurIPS 2017에도 자유 라이선스 표기가 없다. 기존 규칙을 그대로 적용하면 유명 논문이 전멸하고 서비스 컨셉이 성립하지 않는다.

대체 규칙 — 제한을 "논문"이 아니라 "표시 방식"에 건다. 논문마다 사람이 적격 심사를 하면 "모든 AI 논문" 규모에서 병목이 되므로, 편입 자체에는 제한을 두지 않고 화면 표시만 통제한다.

단계규칙근거
인제스트·검색 인덱싱모든 논문 제한 없음공개 배포가 아닌 내부 처리
설명·요약·스토리텔링 생성제한 없음사실·아이디어는 저작권 대상이 아니며 산출물은 자체 생성물
원문 표시 (기본값)짧은 인용(1~2문장) + arXiv 딥링크. 문단 통째 복제 금지저작권법 §28 공표저작물 인용 · §35조의5 공정이용(비영리 교육)
원문 표시 (CC BY·CC0 계열)출처·라이선스 링크·변경 고지 하에 원문 표시 허용라이선스가 2차 변형을 허용
자동 판정: 라이선스는 arXiv OAI-PMH에서 기계로 읽히므로 인제스트 파이프라인이 논문별로 직접 판정하고 표시 정책(short-quote-and-link / full-with-attribution)을 자동 부여한다. 논문 추가 시 arXiv ID만 넣으면 되며 수작업 큐레이션이 없다 — 편입 논문 수에 상한이 생기지 않는 설계.

확장(P3) 시 우선순위: ACL Anthology(ACL·EMNLP·NAACL)는 CC BY 4.0으로 확인됐다. 20편 확장분은 여기서 우선 채우면 원문 표시까지 완전히 자유로운 코퍼스를 얻는다. 기존 "CC BY 우선" 원칙은 폐기가 아니라 확장 단계의 선호 규칙으로 이동한다.
  • arXiv ID·버전 고정 → HTML/PDF 섹션 파싱 → 실패 시 "Abstract-only 모드"
  • 언어 원칙 — 원문 인용은 영어 그대로, 설명은 한국어. 번역 왜곡을 충실성 표본 검사에 포함
  • 퀄리티 리포트 — 인용수·연도·출처 분리 표기, "품질 판정 아닌 참고 신호"

(3) RAG (Retrieval-Augmented Generation)

답 생성 전 논문 원문에서 관련 문단을 검색해 근거로 첨부 — 환각을 줄이는 것이지 없애는 게 아님.

  • 스토리텔링 변환 — 서론을 근거로 비유·이야기 재작성
  • 원문 대조 뷰 — 사실 문장은 원문 문단과 연결, 비유는 "설명용 비유" 라벨로 구분
  • Q&A 챗봇 — 근거 문단 붙여 답변, 없으면 거절
  • 방법론 시각화 — 고정 유형 템플릿(파이프라인·비교·구성요소·반복 루프) 분류 → 스키마 검증 → 렌더 후보 우선순위 자동전환(1순위 실패/저품질 시 2순위로) → 최종 실패 시 텍스트 개요

(4) 다관점 멀티에이전트 P4 고도화

역할이 다른 LLM 호출 여러 개를 병렬 실행. 위험: 같은 모델 계열이 비슷한 환각을 여러 목소리로 반복할 수 있음 → 역할 간 출력에 근거 문단 표시 + 충돌 지점 명시가 완성 조건. 핵심 사이클(P1) 밖이지만 P4에서 실제로 구현할 기능 — 시간 남으면 하는 실험이 아님.

(5) 수준별 학습

"기존 AI 교육은 이산적 난이도라 직접 들어보기 전엔 적합한지 판단 어렵다"는 1차 인터뷰 문제정의에 대응.

  • 온보딩 3단계 수준 선택 → 프롬프트 분기
  • 선수지식 태그 — LLM 자유생성 금지(제각각 생성 방지), 팀이 15~20개 고정 taxonomy 정의 → LLM은 선택+근거만
  • 용어 툴팁으로 흐름 이탈 방지

(6) LLM 평가 · 가드레일

채점 일관성은 게이미피케이션 동기 설계가 성립하기 위한 전제 조건.

4 사전 기술검증 현황

한 줄 요약: 학기 시작 전에 위험한 부분(파싱·검색·거절 등)을 논문 3편짜리 미니 버전으로 미리 돌려본다 — 되면 "새 기술 도전"이 아니라 "이미 검증된 걸 제품으로 완성"하는 일이 됨.

2026-07-27 실측 결과 — 아래 6항목 중 4개를 논문 3편(Attention·ResNet·LLaMA)으로 끝까지 돌려서 실제 수치를 얻었다. 코드는 papercat-core(별도 레포, RN 앱과 분리)에 있고 npm run check 한 번으로 전부 재현된다. 기획서 §3의 P1 정량 통과선("범위 내 80%↑ 근거답변 + 범위 밖 100% 거절")을 이 실측이 충족했다.
검증 항목완료 조건실측 결과
원문 구조화3편 Abstract·Intro·Method를 문단 단위 분리 + 고정 ID완료 182문단(60/59/63), 위치기반 ID(예: 1706.03762:s3:2)로 재실행해도 고정

거절 동작근거 없는 질문 3개 이상에서 거절 응답완료 범위밖 5문항 전부 거절(5/5) — 기준인 "3개 이상"은 충족. 다만 표본 5개라 비율로 환산하지 않는다: 5/5는 실제 거절률이 낮아도 흔히 나오는 결과라 "거절 100%"라고 쓸 근거가 못 된다. 범위내 응답률 14~15/15(재실행 시 변동)
스토리텔링 분리사실 문장·비유 문장 구분 표시미착수 가드 스키마엔 fact/analogy 구분 필드가 이미 있으나, 스토리텔링 전용 프롬프트로 실제 생성해서 확인하는 단계는 아직
비용·처리시간 측정논문 1편 처리시간·토큰수·DB 사용량 기록부분 완료 182문단 임베딩 ≈21,000토큰. 무료 티어(Gemini)라 사전 추정 비용은 $0.03 미만(20문항 생성+임베딩 합산) — 유료 API 기준 정확한 처리시간·토큰 로그는 배포용 계정 전환 후 재측정 필요
청킹 전략 실측 — 그리고 통제 실험이 뒤집은 해석
문단 단위 청킹에서 놓친 3문항(q10·q11·q13)의 정답 문단이 모두 145~180자짜리 초단문이었다 ("RMSNorm을 쓴다" 같은 한 줄). 인접 문단을 700자 목표로 병합하자 Top-5가 80.0%→100%로 올랐다. 여기서 멈췄으면 "청킹 개선으로 20%p 향상"이라고 보고했을 것이다.

하지만 병합하면 청크가 커져서 Top-5가 담는 원본 문단 수도 5개→10개로 늘어난다. "더 잘 찾은 것"과 "더 많이 읽은 것"이 섞인다는 뜻이다. 이를 분리하려고 문단단위 청킹을 K=10으로도 측정(= 병합본과 같은 문단 커버리지)했더니 역시 100%였다.

결론: 향상은 검색 품질이 아니라 커버리지 효과다. 그럼에도 병합을 채택하는 이유는 정확도가 아니라 비용이다 — 같은 100%를 청크 182개→94개(-48%)로 달성하므로 임베딩·저장·API 호출이 모두 절반이다. 오버랩은 정확도를 93.3%로 떨어뜨려 기각했다.
실측 중 발견 — AI 공급자 정정 필요 — §6·§7에 "Claude/GPT API"로만 적혀있는데, Anthropic(Claude)은 임베딩 API를 제공하지 않는다(생성 전용). RAG 검색에는 임베딩이 필수라 OpenAI 또는 Gemini 같은 별도 임베딩 공급자가 항상 하나 더 필요하다. 이번 실측은 OpenAI 계정에 크레딧이 없어 Gemini(무료 티어)로 진행했고, 임베딩·생성 둘 다 무료로 확보됐다 — 단 무료 티어는 모델별 하루 요청 한도(예: 실측한 gemini-flash-latest는 20회/일)가 있어 개발 중 반복 테스트에 걸리기 쉽다. 배포 시에는 종량제(pay-as-you-go) API로 전환하기로 결정 — 이번 실측 규모(3편, 20문항)는 유료로 전환해도 몇 십 원 수준이라 개발 단계부터 결제 계정을 연결해도 손해가 아니다.

6 백엔드 구조 — Supabase (확정, 담당 김성민)

한 줄 요약: 2026-08-02 Supabase로 확정 — 후보 A(별도 Node)·B'(Vercel 서버리스)는 소멸. Auth·Postgres·Edge Functions를 한 곳에서 받고, MongoDB Atlas + Vector Search도 Postgres + pgvector로 대체(같은 DB에서 벡터 검색이 되므로 별도 DB를 붙일 이유가 없어짐).

구성 요소역할현재 상태
Supabase Auth이메일 회원가입·로그인, 세션 유지완료 앱 6개 화면 연결, 끝에서 끝까지 동작
Postgresprofiles(레벨·XP·스트릭) · paper_progress · summary_challenges부분 테이블 생성됨. 마이그레이션 파일이 없어 스키마가 대시보드에만 존재 — 팀원 재현·리뷰 불가
pgvector문단 임베딩 저장 + 벡터 검색(구 Atlas Vector Search 역할)미착수
Edge Functions (Deno)LLM 호출·RAG 파이프라인·가드레일 실행부분 papercat-ai 배포됨(프롬프트→Gemini→텍스트). 아직 앱에서 호출 안 함
남은 일의 대부분은 RAG 레이어 — 현재 Edge Function은 검색 없이 프롬프트를 그대로 모델에 넘기는 구조라, 논문 원문을 읽지 않고 배경지식으로 답한다. 이 상태에서는 §1 차별점 3개(근거 우선 사용 · 근거 ID 연결 · 근거 없으면 거절)가 모두 성립하지 않는다. 검색→근거 첨부→인용 검증→거절 판정을 서버에 올리는 것이 S1의 핵심 작업이며, 논리 자체는 papercat-core에서 논문 3편으로 이미 실측·검증돼 있다(§4).
플랫폼 전환으로 달라진 것
  • DB 이중화 제거 — Atlas(벡터) + 별도 DB(사용자 데이터) 구성이 Postgres 하나로 합쳐짐. Atlas M0의 512MB 게이트 대신 Supabase 무료 티어 기준으로 재산정하되, 3편 ≈2.1MB / 20편 ≈14MB이라 여유는 그대로 큼
  • 인증이 범위에 들어옴 — 기존 계획엔 "게스트ID"만 있었으나 실제 회원가입이 구현됨. 게스트 체험은 Supabase 익명 로그인으로 유지 가능
  • 실행시간 제약은 남음 — Edge Function도 실행 한도가 있어, 긴 생성 작업(스토리텔링)의 상태 DB 저장·재시도·중복 방지 공통 설계는 후보 B'와 동일하게 필요. MVP는 한도 이내 동기 실행, 재시도는 앱의 재요청 버튼 트리거
선결 과제 — 함수 접근 제한: 현재 verify_jwt = false이고 클라이언트가 프롬프트 전문을 보내는 구조라, 함수 URL을 아는 사람은 인증 없이 우리 API 키로 임의 프롬프트를 실행할 수 있다. §2(6) "비용 남용 방어 — API키 서버 전용, 요청/일별 한도"에 해당하며, RAG 담당과 무관하게 먼저 처리해야 한다. 동시에 프롬프트 조립을 서버로 옮겨야 시스템 프롬프트 우회(인젝션)도 막힌다 — 클라이언트는 {paperId, question} 같은 구조화된 값만 전송.

앱↔서버가 주고받을 JSON의 모양과 필드 의미는 별도 문서로 고정했다 — papercat-core/API_CONTRACT.md. 엔드포인트 이름·URL 구조는 자유이나 응답 필드의 의미(status: answered|refused, claims[].type, 인용 ID 포맷 등)는 §4 실측·적대검증으로 확정된 것이라 유지해야 한다. RN 앱은 네이티브 HTTP 클라이언트라 CORS 제약이 없어 통신 설정은 단순.

이 5개는 별도 기능 추가가 아니라 기존 P1~P3 파이프라인을 만드는 방식 자체를 실무 패턴으로 만드는 것 — 검색은 S2 RAG 구축 때, 트레이싱은 S1 첫 코드부터, 평가 자동화는 P2 평가셋과 병렬로 들어간다. 생성형 AI(Claude Code) 전면 활용을 전제로 한 공수 추정 약 7~10일.

12 용어집

문서에 나온 전문 용어를 쉬운 말로. 필요할 때만 펼쳐보세요.

AI·LLM 핵심 개념 (12개)
LLM Large Language Model
ChatGPT·Claude·Gemini 같은 대형 언어 AI. 생성은 Claude/GPT/Gemini 중 무엇이든 되지만, 임베딩(RAG 검색에 필수)은 Claude가 미제공이라 OpenAI나 Gemini가 항상 하나 더 필요하다.
환각 hallucination
사실이 아닌 내용을 그럴듯하게 지어내는 현상.
RAG
답하기 전 관련 원문을 검색해 근거로 삼는 방식. "책 펴놓고 답하기".
임베딩 embedding
글의 의미를 숫자 벡터로 바꾼 것.
벡터 검색
임베딩 간 거리로 "의미가 비슷한" 문단을 찾는 검색.
프롬프트
LLM에게 주는 지시문·질문.
스키마 검증
응답이 정한 형식을 갖췄는지 기계적으로 확인.
LLM-as-judge
다른 LLM 호출이 답변을 채점하게 하는 기법.
골든셋
사람이 미리 정답·점수를 매긴 기준 예시 모음.
홀드아웃
개발 중 절대 안 쓰고 감춰두는 최종 검증용 데이터.
층화 무작위 표본
그룹별로 고르게 무작위 추출하는 표본법.
프롬프트 인젝션
입력 속에 지시문처럼 보이는 문장을 몰래 넣는 공격.
데이터·인프라 (8개)
Supabase
인증·Postgres DB·서버리스 함수를 한 곳에서 주는 백엔드 서비스. 이 프로젝트의 백엔드 스택.
pgvector
Postgres에서 벡터를 저장하고 유사도 검색을 하게 해주는 확장. 별도 벡터 DB 없이 같은 DB에서 RAG 검색이 된다.
Edge Function
Supabase의 서버리스 함수(Deno 런타임). API 키를 서버 쪽에 숨긴 채 LLM을 호출하는 자리.
arXiv
논문을 무료 공개하는 사이트. 원문 주 출처.
Semantic Scholar
논문 메타데이터 검색 무료 API.
CC BY 라이선스
출처표시·변경고지 조건으로 변형·재배포 허용하는 오픈 라이선스.
429 / 백오프
요청 과다 오류코드 / 대기 후 재시도 방식.
RPS
초당 요청 횟수 제한.
캐시 TTL
데이터를 저장해 재사용하는 유효시간.
개발·배포 (6개)
React Native (RN)
JS/TypeScript로 iOS·Android 네이티브 앱을 만드는 프레임워크. bare(CLI) 방식은 Expo 없이 직접 빌드·설정.
Expo
RN 위에서 빌드·배포를 쉽게 해주는 도구 생태계. 이번 프로젝트는 팀 결정으로 제외.
TestFlight
Apple의 베타 배포 플랫폼. 정식 출시 전 테스터에게 빌드를 배포하고 피드백을 받는다.
Route Handlers
Next.js 안에 API 코드를 넣는 기능(백엔드 후보 B'가 API 전용으로 사용).
서버리스 함수
요청 시에만 실행되는 코드. Vercel Hobby는 최대 60~300초 제한.
zustand
React/RN 상태 공유용 가벼운 라이브러리.
Mermaid
텍스트로 다이어그램을 그리는 문법. 방법론 시각화 렌더 후보 중 하나.
평가 지표 (5개)
RAGAS
RAG 품질 자동 채점 오픈소스 도구.
충실성 faithfulness
답변이 근거 문단에 실제 기반했는지.
문맥 정밀도
검색된 문단 중 실제 쓸모 있었던 비율.
문맥 재현율
정답에 필요한 근거를 빠짐없이 찾은 비율.
Top-5
검색 상위 5개 안에 정답 근거가 있는지 보는 기준.

Activities·Environment·Interactions·Objects·Users 사용자 관찰 틀.

HMW
"우리가 어떻게 하면 ~할 수 있을까?" 디자인씽킹 질문법.
GBSA
1차 인터뷰 요청 기관(경기도경제과학진흥원) 약칭.
MVP
핵심 가치를 검증할 최소 실행 가능 제품.
